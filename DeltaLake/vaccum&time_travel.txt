Comprehensive Engineering Notes: Delta Lake Storage Hygiene & Retention (VACUUM and Time Travel)1. Core Architecture & Physical MechanicsDelta Lake maintains separation between its transaction log and physical data storage:Soft Delete vs. Hard Delete:Write operations like OPTIMIZE, UPDATE, DELETE, and MERGE do not erase old files. They perform a soft delete by adding remove actions to the new commit in _delta_log/*.json (tombstoning the files).VACUUM is the only Delta command that executes a hard delete (physical removal) of orphaned/tombstoned Parquet files from cloud storage (S3/ADLS/GCS/DBFS).Metadata vs. Data Storage Lifecycles:VACUUM purges Parquet files; it does not delete .json commit files in _delta_log/.As a result, DESCRIBE HISTORY retains the historical record and audit trail of transactions, even if the underlying data files from older versions have been physically deleted.PlaintextTable Directory / Storage Bucket
│
├── _delta_log/                         <--- NEVER touched by VACUUM (Audit trail intact)
│   ├── 000001.json                     (Points to part-001)
│   ├── 000002.json                     (Tombstones part-001, adds part-002)
│   └── 000003.json                     (Latest active commit)
│
├── part-001-xxxx.parquet               <--- Tombstoned at commit 2
│   └── If age > retention threshold    ───> Physically PURGED by VACUUM
│
└── part-002-yyyy.parquet               <--- Active file (Untouched by VACUUM)
2. Retention Threshold & GuardrailsDefault Window: 7 Days (168 Hours).Why the safety window exists:Query Concurrency: Protects in-flight read queries running on older file versions from failing mid-execution.Rollback & Disaster Recovery: Provides an operational buffer to recover from accidental deletes, bad writes, or failed batch jobs.Streaming Checkpointing: Prevents breaking streaming readers that lag slightly behind the latest commit.The Safety Guardrail:Setting a retention window lower than 168 hours triggers an immediate exception:IllegalArgumentException: requirement failed: The retention duration (...) is shorter than the minimum required...Table-level override (Unity Catalog / Production safe pattern):SQLALTER TABLE <catalog>.<schema>.<table_name> 
SET TBLPROPERTIES ('delta.deletedFileRetentionDuration' = 'interval 0 hours');
3. The Irreversible Trade-Off: Storage Cost vs. Time Travel$$\text{Lower Retention Duration} \implies \text{Lower Storage Footprint \& Costs, but Shorter Time Travel Window}$$$$\text{Higher Retention Duration} \implies \text{Longer Time Travel Window, but Accumulates Tombstoned Storage Overhead}$$Failure Mode: If you query a version whose files were vacuumed:PlaintextDeltaFileNotFoundException: The file ... referenced in the transaction log does not exist.
Once vacuumed, time travel to affected versions is permanently broken.4. SQL Reference & Practical SyntaxDry Run (Always Run First)SQL-- Preview which files will be permanently deleted without actually removing them
VACUUM lab_liquid_db.orders_liquid DRY RUN;

-- Preview deletions for a specific retention window
VACUUM lab_liquid_db.orders_liquid RETAIN 168 HOURS DRY RUN;
Physical DeletionSQL-- Purge files tombstoned longer than 7 days (default)
VACUUM lab_liquid_db.orders_liquid;

-- Custom retention window (e.g., 14 days = 336 hours)
VACUUM lab_liquid_db.orders_liquid RETAIN 336 HOURS;
Table Restoration (Disaster Recovery)SQL-- Restore table state using table version
RESTORE TABLE lab_liquid_db.orders_liquid TO VERSION AS OF 3;

-- Restore table state using a point-in-time timestamp
RESTORE TABLE lab_liquid_db.orders_liquid TO TIMESTAMP AS OF '2026-10-27 10:00:00';
5. Hands-On Lab Observations & Key LearningsDRY RUN on Fresh Tables:Executing VACUUM ... DRY RUN right after OPTIMIZE returned 0 rows.Proved that Delta strictly respects the 168-hour threshold, preventing immediate cleanup of recent files.Unity Catalog Configuration:Session-level Spark configs (SET spark.databricks.delta...) are restricted in Unity Catalog shared clusters.Modifying table retention requires explicit table properties (delta.deletedFileRetentionDuration).Execution of VACUUM RETAIN 0 HOURS:Physically wiped out all tombstoned Parquet files generated prior to OPTIMIZE.Current table query (SELECT * FROM orders_liquid;) remained fully functional because the active compacted Parquet file was never tombstoned.Time Travel Failure Verification:Attempting SELECT * FROM orders_liquid VERSION AS OF 1 produced a DeltaFileNotFoundException.Demonstrated live that Time Travel is constrained by the physical presence of Parquet files, not just the presence of .json log files.6. Technical Misconceptions & TrapsMisconceptionReality"OPTIMIZE deletes old small files immediately."OPTIMIZE only flags them as remove in the JSON log. They remain on disk until VACUUM purges them."VACUUM deletes old transaction history from _delta_log/."VACUUM only deletes Parquet data files. Transaction logs are preserved (governed separately by delta.logRetentionDuration, defaulting to 30 days)."I can run VACUUM RETAIN 0 HOURS daily to save money."Never do this in production. Any analytical query running longer than a few seconds or any simultaneous micro-batch ETL can fail with file not found errors."RESTORE TABLE will bring back deleted files if I ran VACUUM."RESTORE TABLE creates a new commit pointing to old files. If those physical files were already vacuumed, RESTORE TABLE will fail.7. Flashcards for Rapid Knowledge TestingQ1: What is the command to view files eligible for deletion without deleting them?A: VACUUM <table_name> DRY RUN;Q2: What is the difference between delta.deletedFileRetentionDuration and delta.logRetentionDuration?A: deletedFileRetentionDuration (default 7 days) controls how long tombstoned Parquet data files stay on disk before VACUUM removes them. logRetentionDuration (default 30 days) controls how long JSON commit logs in _delta_log/ are kept before being checkpointed and cleaned up.Q3: Can VACUUM cause an ongoing SELECT query on the current version of the table to fail?A: If configured with the default 7-day retention, no. If overridden with RETAIN 0 HOURS while a concurrent query is reading a file that just got replaced by an OPTIMIZE or UPDATE, yes.Q4: Does running VACUUM compact small files?A: No. OPTIMIZE compactor merges small files into large files. VACUUM is strictly a garbage collector that purges files already marked dead by previous operations.8. Summary Checklist for Production PipelinesRun Order: Always run OPTIMIZE first to compact and cluster files, and schedule VACUUM separately (e.g., weekly or bi-weekly).Retention Window: Keep the default 7 days (or minimum 3–7 days) unless data compliance mandates immediate physical removal (such as GDPR right-to-be-forgotten purges).Automated Cleanups: Use Databricks Lakehouse Monitoring / Predictive Optimization where available, or a scheduled maintenance job to avoid unbounded storage bill growth.
